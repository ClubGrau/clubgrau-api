# Reissue the Session Token when a Profile Card save includes name

The header reads `name` from the Session Token issued at Login. Update Own Employee Data persists the new name and returns it in `data`, and that leaves the token claim old until the next Login. After a successful `PATCH /api/employee/me` whose body included `name`, Auth issues a new Session Token with `generateToken` and the live claims (`id`, `name`, `email`, `role`, `status`, `sessionVersion`). The `200` body is `{ data, token }`. The Front replaces the stored token. `sessionVersion` is not incremented, so the previous token stays valid until it expires — this is not revocation and not the Password Reset rule in [ADR 0004](../password-reset/0004-reset-invalidates-existing-sessions.md) / [ADR 0008](../password-reset/0008-session-version-invalidates-jwts.md). A save that omits `name` does not reissue. There is no new route and no password check. A Refresh Token and a `remember` flag are a later PRD. The employees use case does not sign JWTs; `app.ts` injects the Auth command. Same-name retries still reissue, so a token call that fails after the write can be finished without rolling the `$set` back.
